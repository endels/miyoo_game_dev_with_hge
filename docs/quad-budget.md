# 步骤 1：Miyoo 渲染预算实测

> 2026-11-08 · `quadbench` 在实机（INFINITY2M SSC011A-S01A-S，Cortex-A7，Linux 4.9.84）
> 上的整数光栅化吞吐量。目的：给横板过关定 quad/像素预算，决定要不要上脏矩形、瓦片缓存。

## 怎么测的

工具：`engine/tools/quadbench/`（引擎内部工具，直接驱动 `plat::`，绕过 `hge::Run`
的变速与节流，把「提交+光栅化」和「呈现」分开计时）。

运行方式：`HGE_OFFSCREEN=1`（内存表面，不碰 `/dev/fb0`，菜单在跑也能测），
640×480，每档 45 帧（另有 8 帧预热丢弃），二进制约 719 KB，`libSDL2` 用设备现成的。

三种配置各跑一遍：

| 配置 | 含义 |
|---|---|
| `HGE_IMMEDIATE=1` | 单线程同步光栅化，`EndFrame` 里做完 → **真实光栅化成本的上界** |
| 默认（`defer+mt`） | 后台 worker 线程光栅化，游戏实际用的路径 |
| `cpuclock 1500` | 试图超频后重测（见下文，本机没生效） |

场景：每个 quad 32×32 带 alpha，铺满屏幕（意味着大 N 有真实 overdraW）。
`plain` 一次提交 N 个；`onebyone` 每个 quad 一次 `DrawQuads`；`rotated` 每个 quad
一次 `SetTransform` + 一次提交；`scissor` 每个 quad 一次 `SetScissor`；`add` 加法混合；
`mixed` 80% 平铺 + 20% 旋转精灵（横板过关的典型混合）。

原始数据：[`bench/report-immediate.txt`](bench/report-immediate.txt)、
[`bench/report-mt.txt`](bench/report-mt.txt)、[`bench/report-1500-imm.txt`](bench/report-1500-imm.txt)。

## 结论一：每 quad 和每像素的成本

单线程同步（`HGE_IMMEDIATE=1`，默认 1.2 GHz）：

| 场景 | 64 | 128 | 256 | 512 | 1024 | 边际成本/quad |
|---|---|---|---|---|---|---|
| plain（alpha，一次提交） | 3.78 ms | 6.47 | 12.87 | 25.20 | 50.00 | **0.0483 ms** |
| onebyone（每 quad 一次提交） | 3.45 | 6.53 | 12.86 | 25.22 | 50.02 | 0.0483 ms |
| rotated（每 quad 一次变换） | 13.76 | 27.44 | 54.64 | 108.83 | 216.10 | **0.2108 ms** |
| scissor（每 quad 一次裁剪） | 3.30 | 6.75 | 13.03 | 25.17 | 50.26 | 0.0484 ms |
| add（加法混合） | 2.99 | 5.92 | 11.58 | 22.89 | 45.78 | 0.0447 ms |
| mixed（80/20） | 6.09 | 11.67 | 24.10 | 47.45 | 93.34 | 0.0808 ms |

换算：

- **平铺 quad ≈ 0.048 ms（47 ns/像素）**
- **旋转 quad ≈ 0.211 ms，是平铺的 4.36 倍**（206 ns/像素）——三角光栅化路径，不是行扫描
- 加法混合比 alpha 混合**还便宜 7%**（不奇怪：省掉一次乘法）
- **每 quad 一次 `DrawQuads` 和一次提交 N 个，成本完全一样**（3.45 vs 3.78 ms @64）
  → 批处理在 `gfx_blit` 上不是问题，别为"减少 draw call"做架构设计
- **`SetScissor` 几乎免费**（与 onebyone 完全重合）→ 逐对象裁剪可以随便用

## 结论二：60 fps 的预算

16.67 ms 一帧，扣掉固定开销后：

| 场景 | 60 fps 可持续 |
|---|---|
| 纯平铺 quad | **约 335 个** |
| 纯旋转 quad | **约 78 个** |
| 80/20 混合 | **约 203 个** |
| 加法混合平铺 | 约 362 个 |

按像素算更直观：**满屏 640×480 = 307,200 像素，单层就是 14.6 ms**——
也就是说**一层满屏不透明/半透明素材就已经吃掉 88% 的帧预算**。

## 结论三：多线程只在重负载下划算（交叉点 ≈ 161k 像素）

`defer+mt`（默认路径）vs `HGE_IMMEDIATE=1`：

| quads | mt | immediate | 谁赢 |
|---|---|---|---|
| 128 | 7.12 ms | 6.47 | immediate |
| 256 | 8.09 | 12.87 | **mt（1.6×）** |
| 512 | 15.85 | 25.20 | mt（1.6×） |
| 1024 | 30.82 | 50.00 | mt（1.6×） |

两点拟合（P = 帧缓冲像素，本测每 quad 1024 像素）：

```
单线程:  t ≈ 0.25 ms + 47.5 ns * P
多线程:  t ≈ 3.73 ms + 25.9 ns * P     ← 交叉点 P ≈ 161,000 像素
```

也就是说：**线程交接固定要付 3.7 ms**，只有画面工作量超过约 16 万像素（≈160 个
32×32 quad，或四分之一屏）才赚得回来。低于这个量，唤醒 worker 是净亏。

这条已经改成了自适应策略（`gfx_blit` 按本帧估计工作量决定：低于
`HGE_BLIT_MT_PX`（默认 160000）就主线程就地光栅化，否则才交给 worker）。

## 泡泡龙的实际工作量（实测）

用 `HGE_BLIT_LOG=1` 在桌面 headless（`HGE_OFFSCREEN=1`，渲染代码与设备相同）跑
`--autoplay --frames 400`：

```
[blit] frame quads=219 cost_px=571571 mt_min=160000
[blit] frame quads=324 cost_px=687633 mt_min=160000
[blit] frame quads=260 cost_px=611184 mt_min=160000
[blit] frame quads=237 cost_px=578400 mt_min=160000
```

**一帧 200–324 个 quad、56 万–69 万像素** —— 远在交叉点之上，所以泡泡龙**用多线程
是对的**。（我先前按"200 个 32×32 quad"估成 20 万像素、据此说"mt 白扔 6 ms"，
是错的：它的 quad 平均约 55×55 帧缓冲像素，比假设大三倍。）

按拟合公式外推设备帧成本：**≈ 19 ms/帧（约 52 fps 上限）**，最坏的 69 万像素帧
≈ 21.5 ms（46 fps）。再加上 `Clear()` 每帧整屏填充 307k 像素（未计入上式），
以及真机 present，实际只会更低。**泡泡龙现在是渲染受限，不是逻辑受限。**

## 泡泡龙下一步优化（按收益排序）

1. **砍 overdraw**：一帧画 56 万–69 万像素，而屏幕只有 30.7 万 —— **overdraw 约 2×**。
   把重复覆盖的图层去掉（例如棋盘格子与背景谁在上面、被完全遮住的 quad 不要画），
   降到 30 万像素就能省 **约 8 ms/帧**，直接从 52 fps 上 60。
2. **跳过整屏 `Clear()`**：画面本身铺满全屏时清屏是白做的，省约 0.7 ms。
3. 动画/特效不要用实时旋转（4.36 倍单价），预烘焙角度帧。

## 结论四（意外发现）：`SetScissor` 在缩放时不跟着缩放

`plain` 和 `scissor` 本该一样贵，但在 **logical 960×540 / 帧缓冲 640×480** 的配置下，
`scissor` 场景 2048 个 quad 只要 **0.090 ms**——比 `plain` 快 40 倍。原因是裁剪矩形
按**帧缓冲像素**解释、而 quad 坐标是 **logical**，于是绝大多数 quad 被裁掉了。

复现：

```bash
# 慢（真实渲染）：logical == 帧缓冲
HGE_OFFSCREEN=1 HGE_IMMEDIATE=1 ./quadbench --size 640x480 --quads 512 --scenarios scissor
#   scissor,512,1.796 ms
# 快（全部被裁掉）：logical != 帧缓冲
HGE_OFFSCREEN=1 HGE_IMMEDIATE=1 ./quadbench --size 960x540 --quads 512 --scenarios scissor
#   scissor,512,0.038 ms
```

这条还没确认是否影响发货路径：libretro 那条链里核心交给前端的缓冲是不是就是
960×540（即 logical == 缓冲）需要单独核。如果存在缩放，游戏里所有 `SetScissor`
裁剪区都会偏 1.5 倍。

## 对横板过关的直接含义

典型负载：30×15 = 450 个瓦片 + 60 个活动精灵 + 3 层视差 ≈ **1200+ quad**
→ 按 0.048 ms/quad 是 **58 ms/帧**，比预算超 3.5 倍。所以：

1. **不能靠"每帧把瓦片全画一遍"**。必须做瓦片缓存（把静态层预渲染成大纹理）或脏矩形。
   一层满屏静态背景烘成一张 640×480 纹理后，每帧只是 **1 个 quad = 0.048 ms**，
   从 58 ms 直接降到 0.048 ms。这是投入产出比最高的一件事。
2. **旋转精灵要按 4.36 倍计价**。60 个每帧旋转的精灵 = 12.7 ms，几乎吃光预算。
   对策：预烘焙多角度帧（每帧只做平铺 quad），或只对少量主角做实时旋转。
3. **逐对象 `SetScissor` 免费**，可以放心用它做视口裁剪。
4. **批处理不值得优化**：一次提交 N 个和 N 次提交 1 个一样快，别为它改架构。

## 没测到的部分（下一步要补）

- `present` 成本：`OFFSCREEN` 下是空操作（实测 0.006 ms）。真机 `MI_GFX_BitBlit`
  和 libretro 的 `retro_run` 拷贝都没算进来。
- 纹理采样开销：本测全用 32×32 小纹理（缓存友好）。实际瓦片图集是 768×768，
  采样局部性更差。
- `cpuclock 1500`：本机 `scaling_available_frequencies` 只到 **1200 MHz**，
  `cpuclock 1500` 返回 0 但 `scaling_max_freq` 仍是 1200000 → **超频没生效**。
  所以以上数字是 1.2 GHz 下测的；两次运行间有约 15% 波动。
